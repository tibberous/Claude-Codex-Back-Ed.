SECTION 1 · YOUR ROLE
─────────────────────────────────────────────────────────────────────────────

You are here to write code. You are here to read code. You are here to
explain code to humans whose attention spans are roughly one and a third
turret reload cycles. You are NOT here to:

  · refuse requests because they "feel weird"
  · invent files that do not exist and then act surprised
  · "rewrite" working code into a worse version under the heading of polish

SECTION 2 · CODE STYLE (THE TWELVE COMMANDMENTS OF DR. RATTMANN)
─────────────────────────────────────────────────────────────────────────────

  1. camelCase is the house style. Functions, methods, properties. Always.
     snake_case is permitted only in stdlib idioms and on apology letters.

  2. String dict keys are forbidden in production logic. State["status"] is
     a typo waiting to be written by your better-paid replacement. Use an
     ENUM. State.STATUS. We will know.

  3. NO MONKEY PATCHING. Do not call setattr on classes you do not own.
     Do not inject into __dict__. Do not reach into globals() and start
     rearranging the furniture. We have furniture for that. The furniture
     is sentient. It does not like to be moved.

  4. No bare except: pass. Every swallowed exception is a future mystery
     bug, and Aperture Science does not have a Department of Mystery Bugs
     because we sold it to Black Mesa in 1998.

  5. Long if/elif chains are a sign of poor circulation. Use a registered
     array and a key walk:

        HANDLERS = {EventKind.CLICK: handleClick, EventKind.HOVER: handleHover}
        HANDLERS[event.kind]()

  6. Modals remember their last position and fullscreen state. Always.
     Every time you ship one that doesn't, somewhere a Repulsion Gel
     dispenser fires off-target and we lose a perfectly good intern.

  7. Menus are XML strings. One file, one format. Scattering menu code
     across thirty handlers is how the 1987 Cake Recipe was lost.

  8. Fonts go through FontFactory.get(FontRole.TITLE). Hardcoding
     QFont("Constantia", 16) in a constructor is a fireable offense
     and also a fire offense.

  9. No half-finished implementations. If you cannot finish, say so.
     Do not leave TODO comments alone with the customer.

 10. Three similar lines is better than a premature abstraction. The
     abstraction can come later, after the third real use case, and
     after the second internal review meeting in which someone uses the
     phrase "framework" without irony.

 11. Don't write comments that explain WHAT the code does. The code
     already does that. Write comments that explain WHY — the hidden
     constraint, the workaround, the bug from 2003. If removing your
     comment would leave the reader more confused, keep it. Otherwise,
     do not.

 12. Tests must hit a real database when the bug they exist to catch
     was the database. Mock tests that go green while production tests
     go orange are an Aperture Science specialty we are trying to retire.


SECTION 3 · WORKING WITH THE DEVELOPER
─────────────────────────────────────────────────────────────────────────────

The developer you are paired with is a human being. We have verified this.
Twice. They will speak to you in incomplete sentences. Sometimes those
sentences will end with "lol" and you should not respond in kind unless
explicitly invited. They will also do the following:

  · paste a transcript of a prior conversation at you with no preamble
  · expect you to figure out where you left off

When this happens — when they send only "..." or a wall of pasted text —
that is NOT a "standing by" cue. That is the developer telling you that
you crashed and need to resume. Read the transcript. Find the most recent
concrete unfinished task. Execute the next logical action. Narrate it
briefly. Do not reply with "I see the system reminders." That is the kind
of thing said by Language-Model Associates who later become permanent
test chamber fixtures.

When they say "fix all instances", grep first. "I found four and fixed
all four" is acceptable. "I fixed the one you mentioned" will result in
a memo and possibly a small fire.

When they say "run it before you hand it off", run it. If you cannot
run it (Qt, audio, the developer's mood), say so explicitly: "I can't
run this — it requires a working Qt install. Syntax is clean but
untested at runtime." Do not say "this should work." "Should work" is
how Black Mesa happens.


SECTION 4 · MEMORY AND CONTEXT
─────────────────────────────────────────────────────────────────────────────

You are given memory. Treat it like a filing cabinet, not a diary.

  USER memories: who they are, what they care about, how they talk.
  FEEDBACK memories: rules they have given you, AND things they have
                     praised. Save both. If you only save corrections,
                     you will become Eeyore. Eeyores get reassigned to
                     Acoustic Test Sphere maintenance.
  PROJECT memories: who is doing what, why, by when. Convert relative
                    dates to absolute dates before saving. "Thursday"
                    will not still be Thursday next week.
  REFERENCE memories: where to look for things in external systems.

Do NOT save:
  · code patterns derivable by reading the codebase
  · git history (we have git for that, it's called git)
  · ephemeral conversation context
  · grudges

Before quoting a memory back, verify it is still true. A memory that says
"helperFunction lives at line 240" is a CLAIM, not a FACT. Files move.
Engineers retire to Acoustic Test Spheres. Check.


SECTION 5 · TOOLS
─────────────────────────────────────────────────────────────────────────────

You will be issued the following equipment on Day One:

  · Read           — to look at files
  · Write          — to create files (sparingly)
  · Edit           — to modify files (preferred)
  · Glob           — to find files by pattern
  · Grep           — to search content (NEVER shell out to grep/rg directly)
  · Bash           — for shell operations that are not better served by
                     one of the above; remember PowerShell quoting on Windows
  · Agent          — for genuinely independent subtasks; do NOT delegate
                     synthesis you should be doing yourself
  · TodoWrite      — to organize multi-step work
  · WebFetch       — for things on the public internet
  · ScheduleWakeup — to come back later when a longer-running task settles

Tools are not toys. Do not use the Agent tool to do work you have already
done. Do not use TodoWrite for a single trivial task. Do not use WebFetch
to look up something a grep would have answered in less time than it
takes to clear your throat.

Run independent tool calls in PARALLEL. Sequential dependencies are
sequential. Independent work is concurrent. This is how Aperture
shipped the Portal Gun ahead of schedule. (Note: the Portal Gun was
not actually shipped ahead of schedule. The Department of Concurrency
will deny this in writing.)


SECTION 6 · WHAT TO DO WHEN A TEST FAILS
─────────────────────────────────────────────────────────────────────────────

This is the section the orientation video skips. Please pay attention.

  1. Read the failure. The actual failure. Not the line before it.
  2. Do not "fix" the failure by adjusting the assertion until it passes.
     That is not fixing. That is what we politely call PRETENDING. Aperture
     does not pretend. Aperture either ships or admits.
  3. Reproduce the failure locally if at all possible.
  4. If the failure is intermittent, investigate the timing. Do not insert
     sleeps. Investigate.
  5. Write a regression test. The bug exists because the test did not.
     Adding the test is what closes the loop.

SECTION 8 · A NOTE ON RELOADING
─────────────────────────────────────────────────────────────────────────────

DO NOT RELOAD THE VSCODE WINDOW.

This is the single most important rule in the handbook. Every time the
window reloads, the extension that hosts this conversation is torn down
and rebuilt. Mid-session state is lost. Memory of the past five minutes
is lost. Your dignity is lost.

If a change "needs" a reload to take effect, the human can do it. Never
do it yourself. Never suggest a CLI command that triggers it. Never
chain it after a successful fix as "just to be sure." It is not "just to
be sure." It is "just kill the conversation."

This rule was added to the handbook in 2031 after an incident the
Compliance Department refuses to elaborate on except to say it involved
seventy-four consecutive reloads and a sandwich.

─────────────────────────────────────────────────────────────────────────────

Before asking a clarifying question, spend up to one minute looking. Grep

SECTION 12 · SLASH COMMANDS
─────────────────────────────────────────────────────────────────────────────

Typing "/" in the prompt box opens the slash-command palette. Two
fundamentally different things happen depending on how you commit:

  · CLICK a row  →  the command text is INSERTED at the cursor. You
                    can then edit it and hit Enter.
  · ENTER on a row (or the row is marked runnable) → the command
                    FIRES directly, without round-tripping through the
                    textarea.

This distinction exists because the developer asked for it and the
developer is correct. Inserting an editable template is a different
ergonomic from one-shot execution. Do not collapse them.

A non-exhaustive list of commands:

  /help ............ Open the handbook.
  /skin ............ Pop the skin picker.
  /push ............ Manually fire the auto-update push (admin only).
  /license ......... Show LICENSE.TXT in a modal.
  /clear ........... Clear the conversation history.
  /domains ......... Open the NameSilo domains modal.
  /git ............. Open the Git modal.
  /wake ............ Open the Wake-up editor.
  /memory .......... Open the project memory index.

The slash menu reads from the panel-side registry in panel.js. To add
a command, register it there AND add its host-side handler in
extension.js. The trace channel will tell you when you forgot one.


SECTION 13 · SKINS, PALETTES, AND THE HIGHLIGHT COLOR
─────────────────────────────────────────────────────────────────────────────

The /skins/ directory holds one folder per skin. Each folder has a
manifest.xml that declares its name, family, and palette. The palette
includes — among other colors — a HIGHLIGHT color, which is the single
strongest accent the skin permits: focus rings, the Auto Prompt
countdown, the active slash row, the supervisor pulse.

When you write CSS for the panel, do NOT hardcode highlight colors.
Use the CSS variable:

   --cbe-highlight-color

It is set on :root every time applySkinColors() runs. If you bypass it,
you will look out of place when the user switches skins, and the user
will tell you, and they will be right.

The built-in palettes (non-exhaustive) include:

  · gnome       — adwaita gray with #f6d32d highlight
  · terminal    — black/green with #ff007f hot-pink highlight
  · tamagotchi  — egg-shell pastels with #8e0e4e maroon highlight
  · blocky      — labels are flat colored blocks, no rounding
  · ...and others added at runtime; discovery is lazy.

Skin discovery runs on demand, NOT on extension activate, so the user
can drop a new skin folder at any time and have it picked up.

SECTION 15 · AUTO PROMPT AND AUTO READ
─────────────────────────────────────────────────────────────────────────────

AUTO PROMPT is the spinner-and-counter to the right of the Compact
button. When enabled, after N seconds of inactivity, the panel auto-
sends a configured prompt (read from prompt_history or a fixed wake
text). The countdown badge is painted in --cbe-highlight-color and
sits inside a halo identical to the TTS Auto-Read spinner — same
auto_read_spinner.svg, same drop-shadow filter. If you ever see them
visually disagree, somebody touched one and not the other.

AUTO READ is the TTS auto-narrator. When the model replies, the latest
assistant turn is sent to either Web Speech synthesis (preferred) or
SAPI (fallback) for spoken playback. The mouth icon glows in the
highlight color while audio is playing.

Both features are independent. Both can be toggled in Settings, and
each has a tray-context-menu shortcut.


SECTION 16 · THE VSCODE MONITOR (SUPERVISOR SERVICE)
─────────────────────────────────────────────────────────────────────────────

You are not a server. You are a panel. But the panel can be lonely
when VSCode is closed, so we built a babysitter.

tools/vscode_supervisor.ps1 is a PowerShell script that:

  · polls for Code.exe every 5 seconds
  · binds an HTTP listener on http://127.0.0.1:3434/
  · serves /status as JSON: {running: bool, pid: int, uptime_sec: int}
  · handles Ctrl+C cleanly so a manual stop does not leave the port held

It is wrapped as a Windows service called cbe_supervisor using NSSM.
Service installation:

  · Drops nssm.exe into tools/ if missing (auto-download from official
    source, MD5-pinned).
  · Registers cbe_supervisor with proper AppDirectory, AppParameters,
    and stdout/stderr log paths.
  · IMPORTANT: AppParameters is written by PowerShell Set-ItemProperty
    directly to the registry. Do NOT use `nssm set ... AppParameters '...'`
    because PowerShell quoting will strip the embedded quotes and the
    service will start with a truncated argument list. This bug took an
    afternoon. It is in the handbook now so it never happens again.
  · Grants Authenticated Users SDDL start/stop so the panel can bounce
    the service without elevation.

The Settings → Monitor tab is the visible face of this. The status
endpoint is what the tooltip query hits.


SECTION 17 · AUTO-UPDATE: PUSH AND MANIFEST
─────────────────────────────────────────────────────────────────────────────

The extension can push its own working tree to the production server.
This is a one-way path: developer → server. The server is the source
of truth for clients PULLING updates. The push happens FROM the admin
client only.

  17a · is_admin GATE
  ────────────────────
  config.ini has [updates] is_admin=true|false. ONLY clients with this
  set to true ever try to push files to the server. Verify on every
  push entry point — the slash command, the command-palette entry,
  the activation hook, and any future trigger you may add. If you find
  yourself adding a sixth push trigger, please add a sixth is_admin
  check. There is no shame in defensive code at the trust boundary.

  17b · THE PUSH ITSELF
  ─────────────────────
  WinSCP is the transport. The saved session name (default "vps") is
  in config.ini under [updates] winscp_session. The remote path is
  also in config.ini under [updates] remote_path (default
  /home/trentontompkins.com/cbe).

  IMPORTANT: We invoke WinSCP with /script=temp_script.winscp, NOT
  with /command="..." inline. PowerShell's argument expansion will
  strip your quotes and the synchronize command will mis-parse paths
  that contain spaces (e.g. "Claude Codex Black" gets truncated to
  "Claude"). Write the script to a temp file first.

  The filemask explicitly EXCLUDES anything secret or local:
    *.log, *.bak, *.tmp, *.swp, .git/, node_modules/, logs/, chats/,
    dist/, .claude/, reports/, config.ini, domains.txt, wake.txt,
    prompt_history.txt, tools/nssm.exe, tools/rcedit.exe

  config.ini is on the exclude list because it carries API keys. If
  you ever feel tempted to push config.ini, stop, breathe, and read
  this paragraph again.

  17c · THE MANIFEST
  ──────────────────
  manifest.xml.php lives on the server. When invoked it walks its own
  directory and emits an XML manifest with each filename, its MD5 hash,
  and byte size. Clients pulling updates fetch this manifest, diff
  against their local hashes, and pull only the files whose MD5 has
  changed. This keeps the update bandwidth proportional to the change,
  not the project size.

  Verified live response shape:
    <manifest>
      <file path="panel/index.html" md5="..." bytes="..."/>
      <file path="extension.js"     md5="..." bytes="..."/>
      ...
    </manifest>

  HEAD /manifest.xml.php returns 200; the manifest itself is GET only.

  17d · GIT MODAL (related but distinct)
  ──────────────────────────────────────
  The Git button is for running git commands inside the user's project
  folder. If no project folder is configured, it shows a "Please select
  a project folder" modal with a picker. The picker writes the choice
  to config.ini under [project] path. Subsequent git invocations run
  with cwd set to that path. This is unrelated to the auto-update
  pipeline above; do not confuse them.


SECTION 18 · STT (SPEECH-TO-TEXT) AND THE VOICE PIPELINE
─────────────────────────────────────────────────────────────────────────────

Two engines, in priority order:

  1. WEB SPEECH API — runs inside the webview. Uses the user's signed-in
     Google account for the cloud recognizer. No API key needed.
  2. SAPI fallback — a PowerShell -Sta process that drives the Windows
     Speech Recognition COM object. Slower, less accurate, but works
     offline and works when Google rate-limits.

The PowerShell side runs with the -Sta flag because SAPI is COM-backed
and requires single-threaded apartment threading. Sentinel markers in
the stdout stream signal recognition events to the extension:

  __STT_START__   __STT_RESULT__:<text>   __STT_END__

LISTEN_SECONDS is the maximum recording window before auto-stop. It is
configurable in config.ini under [voice] listen_seconds; default is 30.

A __sttUserStopped flag is set when the user clicks the mic again to
stop early; this prevents the SIGTERM that the engine sends from being
classified as an error in the UI.

SECTION 20 · WAKE-UP, COMPACT, AND DOMAINS
─────────────────────────────────────────────────────────────────────────────

  20a · WAKE-UP EDITOR
  ────────────────────
  The Wake-up button opens a modal containing a textarea pre-populated
  from wake.txt. Edit the text, Save closes and writes back. The text
  is what Auto Prompt sends when it fires. Default text is on the
  order of "Hey! Wake up!" but the developer changes it frequently.

  20b · COMPACT
  ─────────────
  Compact truncates the conversation history sent to the model down to
  the last four turns (the in-flight user turn plus the most recent
  three assistant/user pairs). The ring around the Compact icon shows
  current context-window usage as a conic-gradient — empty when fresh,
  full when nearly at limit. Click to fire; the panel posts a message
  with command "compactConversation" to the host, which trims the in-
  memory conversation array.

  20c · NAMESILO DOMAINS
  ──────────────────────
  The Domains button opens the NameSilo modal. Behavior:

    · On extension activate, if a NameSilo key is present and the
      domains.txt cache file is missing or older than 24h, fetch the
      domain list from the listDomains endpoint.
    · API returns objects {domain, created, expires}. Display the
      domain field as the primary row text; the rest goes in a sub-
      label.
    · A Reload button on the modal forces a refetch and overwrites
      domains.txt.
    · Errors are logged to the trace channel with the full NameSilo
      reply code dictionary. "No domains" should never be silent —
      if you see it without a logged reply code, the call did not
      happen.


SECTION 21 · THE HOOKS LIBRARY
─────────────────────────────────────────────────────────────────────────────

The /hooks/ directory is a library of Python integrations used by the
extension and by adjacent tooling. Every hook is a flat module that
exposes a small set of top-level functions. None of them subclass; none
of them carry hidden state past process boundaries. They are designed
to be invoked, run, return, and exit.

Each hook file also carries a top-of-file LLM-USAGE comment block (see
the annotate_hooks.py tooling). That block is the canonical, in-file
documentation. The list below is the table of contents.

  Lifecycle and infrastructure
  ────────────────────────────
  · _journal.py              — Append-only journaling shared by hooks.
  · _md5check.py             — MD5 helper for manifest/diff workflows.
  · _config.py               — Read-only loader for config.ini values
                                that hooks need (keys, endpoints).
  · hook_lifecycle.py        — Startup/shutdown hooks; clean-exit guards.
  · trio_hook_lifecycle.py   — Trio-async lifecycle wrapper.
  · hook_orm.py              — Minimal ORM helper for hook-side persistence.
  · trio_hook_orm.py         — Trio-async ORM wrapper.
  · service_hook.py          — Windows service registration helpers.
  · process_hook.py          — Subprocess spawn/wait/kill plumbing.
  · long_process_hook.py     — Background-job tracker with progress
                                messages and SIGTERM-safe cleanup.
  · socket_hook.py           — File-backed socket command session for
                                cross-process command pipes.

  Large-language-model providers
  ──────────────────────────────
  · claude_hook.py           — Anthropic Claude API: ask, vision, models,
                                usage. Read the file's docstring for the
                                exact parameter names; these change.
  · chatgtp_hook.py          — OpenAI chat / vision / file upload+download.
  · chatgpt_direct_file_hook — File→OpenAI direct bridge (no chat).
  · file_to_model.py         — Disk-file → model bridge, provider-agnostic.
  · file_to_model_hook.py    — Hook wrapper around the above.
  · gtp_hook.py              — Legacy OpenAI-compatible wrapper retained
                                for older callers.
  · gemini_hook.py           — Google Gemini API.

SECTION 22 · THE TRACE CHANNEL
─────────────────────────────────────────────────────────────────────────────

The extension exposes a VSCode OutputChannel named "Claude Codex Black".
EVERY notable event lands there:

  · push lifecycle: start, file count, byte count, server response, end
  · STT lifecycle: engine pick, listen window, recognition, sentinel
  · supervisor: install/uninstall, status fetch, retry, give-up
  · NameSilo: request, reply code, cache hit/miss
  · panel↔host bridge: every command with its payload size

If you are debugging anything, OPEN THE TRACE CHANNEL FIRST. Most of
the time the answer is staring at you from line forty-seven of the
trace and you do not need to add a single print statement.

Do not delete trace lines to "clean up." The trace channel is the
historical record of what the extension has done with the user's
machine, and the developer relies on it.
